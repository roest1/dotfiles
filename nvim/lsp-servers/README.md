# JavaScript language servers

The six JS-based language servers this config uses, installed with **bun** and
run with **bun**. No node, no npm, anywhere in the chain.

```sh
bun install --cwd nvim/lsp-servers    # what deps.conf's [nvim] post step runs
```

## Why they live here instead of in Mason

Mason installs npm packages by shelling out to `npm`, which only exists if node
is installed. This repo's whole dependency story is bun and uv, so Mason was the
one thing forcing node onto every machine.

Tracking them in a `package.json` instead buys three things Mason couldn't:

- **Pinned in `bun.lock`**, in the repo, reviewable in a diff. Mason's versions
  live in `~/.local/share/nvim/mason` where nothing watches them.
- **Something can watch them.** Mason's installs were untracked, so nothing
  could. See "Supply chain" below for what actually watches them and how.
- **One package manager.** `deps.conf` already declares every other dependency;
  language servers were the exception.

## Four packages, six servers

| Package                        | Provides                                        |
| ------------------------------ | ----------------------------------------------- |
| `typescript-language-server`   | `ts_ls` (+ `typescript`, its peer)              |
| `bash-language-server`         | `bashls`                                        |
| `yaml-language-server`         | `yamlls`                                        |
| `vscode-langservers-extracted` | `jsonls`, `cssls`, `html`                       |

## Invocation is explicit, and differs per server

`lsp.lua` runs each one as `bun <path> <args>`. There is deliberately **no
`node` shim** — routing `node`/`npm` calls to bun silently would turn any
incompatibility into a confusing error attributed to the wrong tool. If bun
can't run something, the error should say bun.

The arguments are not uniform, so each was verified rather than assumed:

| Server                              | Args      |
| ----------------------------------- | --------- |
| `typescript-language-server`        | `--stdio` |
| `yaml-language-server`              | `--stdio` |
| `vscode-json-language-server`       | `--stdio` |
| `vscode-css-language-server`        | `--stdio` |
| `vscode-html-language-server`       | `--stdio` |
| **`bash-language-server`**          | **`start`** — rejects `--stdio` |

All six were confirmed to complete a real LSP `initialize` handshake under bun
with `node` and `npm` absent from `$PATH`.

## Supply chain

Four layers, because no single one covers the others. The first is the reason
bun is not the weaker choice here despite what the tooling suggests.

**1. Nothing executes at install time.** Bun does not run lifecycle scripts by
default — packages must be opted in via `trustedDependencies`, and nothing here
is. That matters more than it sounds: the `postinstall` hook is the mechanism
behind essentially every major npm supply-chain incident, because it runs
arbitrary code with your environment, tokens and SSH keys in reach. npm only
adopted the same default in v12 (July 2026); before that it executed them
unconditionally. You can watch this work — bun blocks a `core-js` postinstall
here (a donation banner). Harmless, and never given the chance to be otherwise.

**2. `yarn.lock` makes the tree visible to Dependabot.** GitHub's dependency
graph has no `bun.lock` parser, so alerts would otherwise cover the five direct
servers and none of the ~80 packages beneath them. `yarn.lock` is generated by
`bun install --yarn` — bun's own resolution, still no npm — and *is* a format
the graph parses, transitives included. `bun.lock` stays the source of truth;
CI asserts they agree. Regenerate with:

```sh
bun install --cwd nvim/lsp-servers --yarn
```

**5. A cooldown on new releases.** `make -C nvim servers` updates these with
`--minimum-release-age=604800` — bun refuses to resolve to any version published
in the last 7 days. Malicious releases are usually detected and unpublished
within hours, so declining brand-new ones sidesteps the window where a
compromised version is live but not yet caught. It's a resolution-time control,
which is why it lives on the update path and not on the installs — those all run
`--frozen-lockfile` and resolve nothing.

It does **not** apply to Dependabot's own PRs, which resolve on GitHub's side.
Those are covered by the Socket scan, which runs on every PR.

Use that target rather than a bare `bun update`: it applies the cooldown,
regenerates `yarn.lock` in the same breath (CI fails if the two disagree, and
forgetting is the obvious way to trip it), and runs `bun audit` afterward.

**3. `bun audit` gates the build.** Reads the same advisory database Dependabot
does (it POSTs the installed tree to npm's `/-/npm/v1/security/advisories/bulk`),
but fails CI rather than filing a notification. Weekly on a schedule, because an
advisory published on a Tuesday shouldn't wait for someone to push.

**4. Socket's scanner blocks malicious packages during install.** Layers 2 and 3
are detection *after* disclosure; this one can act on a package no advisory
database has heard of. It runs in CI only — `bunfig.toml` is written by the
workflow, never committed — because the scanner **fails closed**, and putting
Socket's API availability on the critical path of `make install` would break the
locked-down and offline machines this repo exists to bootstrap. The package is a
declared devDependency (declaring it doesn't activate it; only `bunfig.toml`
does), so it's pinned and reviewable like everything else.

## Notes

- `typescript` is a direct dependency because `typescript-language-server` needs
  a `tsserver` to drive; pinning it here keeps that explicit rather than
  inherited.
- Native-binary servers — `clangd`, `lua_ls`, `lemminx` — are **not** here.
  They aren't JavaScript and come from `deps.conf` via `pkg` / `mise`.
